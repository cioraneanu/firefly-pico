---
title: Profiles
description: Keep a set of defaults for each way someone uses Pico.
---

A profile groups preferences that shape how Pico behaves. Switching profiles changes the working context, such as the default account, currency, tags, or enabled features. It does not create a separate Firefly III account.

## An everyday example

At home, a user may normally spend from one account in their local currency. On a trip, they want a different currency and a trip tag on new transactions. A travel profile lets them keep both setups and switch between them instead of repeatedly editing settings.

Profiles can be selected from the mobile profile control or the desktop sidebar. Their saved records belong to Pico and are associated with the access token. Browser state also holds the current settings so screens can use them immediately.

## Defaults are starting values

A profile helps prepare new work. When you add a default, be explicit about when it applies: opening a new transaction, interpreting assistant input, or enabling a screen. Avoid treating a preference change as a reason to rewrite existing financial records.

This distinction matters when testing. Open a fresh form after switching profiles and check the intended fields. Also confirm that loading an existing transaction still shows the transaction's saved values.

## Adapting preferences

Start in `front/stores/profileStore.js` and find a nearby preference with the same kind of behavior. Trace where it is read and how profile data is saved before adding your own. Some settings describe the connection or browser session rather than the selected profile; the app store and profile store have different responsibilities.

[State and profiles](/guide/state) expands this into the frontend's shared-state model.
