title: Contributing
description: Make a focused change that is easy to understand and review.
---

Begin by describing the user problem and the behavior you want to improve. The project's contribution guidance asks contributors to discuss proposed changes in an issue before opening a pull request and to target the `dev` branch. Confirm the repository's current guidance when preparing your contribution.

## Get a working baseline

Follow [From source](/installation/manual) and try the affected workflow before editing. Read the repository's `AGENTS.md` and nearby implementation. This guide explains the design; the repository instructions and source define the exact local conventions.

Keep one change focused on one outcome. Reuse existing UI components and data-flow patterns, and avoid unrelated formatting or dependency changes. A clean diff helps reviewers see the behavior that matters.

## Validate the change

For frontend work, run `npm run lint:fix`, `npm run lint`, and `npm run build` from `front/`. Review any automatic formatting changes so unrelated files do not become part of the contribution. For backend work, run `php artisan test` or the relevant test target from `back/`.

For a UI change, inspect the affected mobile and desktop layouts and both themes. For saved data, reload after saving so you test persistence as well as immediate feedback. Parse edited locale JSON files and check that labels fit their controls.

## Explain the result

A useful pull request says what users experienced before, what they experience now, and how you checked it. Mention migrations or changed API behavior when present. Screenshots help reviewers understand a visible change; a long tour of every helper usually does not.

If your change introduces a concept, update the guide page that first explains it. If it only changes an implementation detail, keep the documentation at the level readers need to understand the feature.
