Most Pico features connect three things: a financial record, a convenient way to edit it, and preferences that make the next edit faster.

![The browser sends requests to the Pico API. The API connects to Firefly III for financial records and to the Pico database for additional information.](/images/system.svg)

## The concepts

| Concept | Meaning in Pico | Everyday example |
| --- | --- | --- |
| Entity | A kind of record the app works with | A category or transaction |
| Extra field | Information Pico adds to a Firefly III record | A category icon |
| Template | Saved values to apply to a transaction form | The usual account and tags for a bill |
| Profile | A saved set of app preferences and defaults | Everyday spending versus a trip |
| Store | Shared browser state used by multiple screens | Categories available in both a list and a picker |
| Repository | The frontend's route to an API resource | Loading or saving categories |
| Transformer | Translation between API values and form values | Turning a saved icon identifier into a picker value |
| Composable | Shared behavior a Vue screen can use | Loading, saving, and deleting an item |

## Follow one change

Suppose you change a category's name and icon. The form holds the edit. Shared form behavior asks the model's transformer to prepare the values and its repository to send the request. The Pico backend updates the Firefly III record and saves its own extra information. The frontend updates the shared category list so other screens can display the result.

You do not need to implement that whole chain for every change. A spacing adjustment belongs in the theme. A different starting value usually belongs in defaults. A new stored field crosses more layers because it needs somewhere to live.
