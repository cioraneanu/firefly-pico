The previous chapter ended with a store update after saving. A store is the shared state that lets multiple screens agree about the same data. Pico uses Pinia stores, and many of their values persist in browser local storage.

## Lists and dictionaries serve different views

The category store holds a list for iteration and derives a dictionary keyed by identifier for lookups. A list page needs the collection; a picker or transaction display may need one category. Both should draw from the same source.

The store's fetch operation loads data through the repository and transformer discussed in [Data and ownership](/guide/data). This is also where feature preferences can affect the available data: the category store, for example, clears its list when categories are disabled.

## Cached does not mean current

Pico synchronizes shared data, and users can refresh lists. A locally cached list can be older than the server. When adding a save or delete flow, follow the existing page's store update or refresh pattern so the visible collection reflects the completed action.

The PWA and persisted state help the app launch and reuse data, but do not assume a write is saved remotely just because a form is visible offline. The normal API response remains part of the save flow.

## Profiles influence behavior

The profile store supplies preferences such as defaults and feature toggles. The app store covers broader application state, including connection and layout concerns. Place a new preference alongside settings with the same purpose and lifetime.

When a screen depends on a selected profile, derive the visible result from that state where possible. Avoid maintaining a second copy of values that can be computed. For a new setting, trace persistence as well as its immediate effect on the page.

Use `front/stores/categoryStore.js` as the small collection example and `front/stores/profileStore.js` for preferences. Next, [Your first adaptation](/guide/adapting) puts the layers together.
