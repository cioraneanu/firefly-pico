title: Your first adaptation
description: Plan a small change by following one existing feature through the app.

You have now seen the user workflow, data ownership, screens, and shared state. Use that order to decide what a change needs before editing files.

## Start with one visible outcome

Suppose you want a short Pico-only note on a category. Define the result first: the user can edit the note, save it, and see it again after reloading. That immediately tells you the note needs backend storage rather than just a new input.

Categories already demonstrate a Pico-only icon. Follow that feature through the code and adapt the same pattern for the note.

## Follow the existing layers

1. **Storage:** add a migration and declare the extra field on the backend model. Follow nearby validation and response conventions.
2. **Data mapping:** give the frontend model an appropriate empty value and include the field in the transformer used for reads and saves.
3. **Form:** add a UI-kit field and connect it to the item's attribute using the page's existing binding pattern.
4. **Shared state:** keep the page's save handling consistent so lists and later edits see the returned value.
5. **Presentation:** add translations in every supported locale, then inspect the mobile, desktop, light, and dark states affected by the input.

This is a map for finding the relevant code, not a requirement to change every layer for every feature. If you are only changing spacing or a label, the work is much smaller.

## Prove the intended behavior

Create a category with the note, reopen it, change the note, and reload the app. Check that the ordinary category fields still behave as before. Use a development account, because these actions also interact with Firefly III.

Run the frontend lint and build commands for frontend changes. For backend behavior, run the relevant Laravel tests and add focused coverage when the new persistence logic needs it. Inspect the diff for unrelated changes before sharing it.

## Keep the next change easy

Prefer the existing repository, transformer, composable, and UI-kit patterns. A small addition should be easy to recognize next to the icon field you used as a reference. Reach for a new abstraction only when the current change demonstrates a real need.
