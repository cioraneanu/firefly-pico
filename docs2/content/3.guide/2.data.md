The overview introduced two backends: Pico and Firefly III. The important distinction is ownership. Firefly III owns the financial records; Pico stores additions that support its own interface and workflows.

## Three places data can live

| Place | Responsibility | Example |
| --- | --- | --- |
| Firefly III database | Financial records used across Firefly clients | Category name, transaction amount |
| Pico database | Pico-specific records and extra fields | Category icon, transaction template |
| Browser state | Current interaction and cached data | Open form, cached category list |

A browser cache helps the UI respond quickly. It is not a replacement for backend persistence. An edit that must survive a cleared browser needs an appropriate server-side home.

## A category across the boundary

Categories arrive in a JSON:API-style shape: an identifier and type alongside an `attributes` object. The name therefore lives at `attributes.name`. This same shape makes it possible for the backend to add Pico fields to Firefly III responses.

The frontend model defines an empty category and connects it to its repository and transformer. The repository handles requests to the category endpoint. The transformer adapts the values for the form, including the icon picker, and prepares the values for saving.

On the backend, `CategoryController` uses `BaseControllerFirefly`. Firefly III handles the category record, and the category model declares `icon` as a Pico extra field. Reads combine the available information so the frontend can work with one category object.

## Choose the smallest route for a change

A display-only calculation can stay in the frontend. A value already supported by Firefly III should follow that API's model. A new Pico-only value needs Pico persistence and the corresponding response/form mapping. A completely Pico-owned resource follows its own controller and storage path.

Read `front/models/Category.js`, `front/repository/CategoryRepository.js`, `front/transformers/CategoryTransformer.js`, and `back/app/Models/Category.php` together. They are a compact example of the boundary; the base classes contain the shared implementation.
